# Contributing

## Setup

Install Node.js 22 or 24, npm, rustup, and the native compiler/linker tools for
your operating system. The repository's `rust-toolchain.toml` selects the Rust
version and required components.

```bash
git clone https://github.com/psht13/avl-tree.git
cd avl-tree
npm ci
npm run build
npm test
```

Use `npm ci`, not an unconstrained dependency install, when reproducing CI.
Native builds are release builds unless `npm run build:debug` is requested.

## Architecture

Production responsibilities are intentionally narrow:

- `src/tree.rs` owns the safe Rust AVL implementation.
- `src/lib.rs` translates the stable JavaScript methods to the core.
- `native.js` and `native.d.ts` are generated by NAPI-RS.
- `index.js` and `index.d.ts` preserve the package's default constructor export.

Keep business logic out of the JavaScript loader. Avoid unsafe code, parent
pointers, arenas, or generic frameworks unless measurements show a material win
that justifies the maintenance cost.

### NAPI-RS version policy

The Rust crate remains on the maintained NAPI-RS 2 patch line (`napi` 2.16.17
and `napi-derive` 2.16.13), with `dyn-symbols` for portable addon loading. The
current NAPI-RS 3 CLI is used for deterministic loaders and platform packages;
that packaging flow does not require migrating the Rust API.

NAPI-RS 3 was prototyped against the complete Node contract, but it did not
remove wrapper code or add a required target. An unnecessary Rust API major
migration was therefore rejected. Revisit this only when the
[migration guidance](https://napi.rs/docs/more/v2-v3-migration-guide) identifies
a concrete correctness or packaging benefit for this addon.

## Tests

```bash
npm run test:rust
npm run build
npm run test:node
npm run test:package
```

Rust tests cover rotations, deletion shapes, ordering, height and balance
invariants, length accounting, boundary keys, deterministic stress sequences,
and exact legacy dump formatting. The property test generates 256 operation
sequences of up to 127 operations and compares every step with
`BTreeMap<i32, String>`.

Node tests use the built-in `node:test` runner and exercise the compiled addon as
a CommonJS, ESM, and package consumer. Package tests create real npm tarballs,
install them into a temporary project, run both module systems, and compile
CommonJS and ESM declaration consumers.

When public behavior changes, add both a Rust core test and a Node contract test
when applicable. Do not weaken conversion, return-value, or dump compatibility
without documenting it as a major-version change.

## Coverage

Install the pinned coverage tool once:

```bash
cargo install cargo-llvm-cov --version 0.8.7 --locked
rustup component add llvm-tools-preview
```

Then run:

```bash
npm run coverage
```

Rust line coverage must remain at or above 90%. The AVL core target is at least
95%. Node's V8 report covers only handwritten JavaScript; it does not measure
the Rust native implementation. LCOV files are written below
`target/coverage/`.

## Benchmarks

```bash
npm run benchmark:rust
npm run benchmark:node
```

Criterion fixtures and Node benchmark datasets are deterministic and created
outside timed sections. Compare changes using release builds, the same harness,
and an otherwise idle machine. Do not add noisy benchmark thresholds to normal
pull-request CI. Investigate a representative regression greater than roughly
5% and either fix it or explain the tradeoff in `BENCHMARKS.md`.

See [BENCHMARKS.md](BENCHMARKS.md) for the workloads, baseline commands, and
recorded environment.

## Formatting and linting

```bash
npm run format
npm run format:check
npm run lint
cargo clippy --all-targets --all-features -- -D warnings
```

Formatting commands that write files are separate from CI checks. Before a pull
request, run the complete deterministic gate:

```bash
npm run validate
```

## Pull requests

- Keep production changes focused and preserve the published JavaScript API.
- Include a test for correctness changes and measurements for performance
  claims.
- Do not commit `.node` files, tarballs, `target`, coverage, or benchmark output.
- Regenerate `native.js` and `native.d.ts` with `npm run build`, then verify
  `npm run native:check`.
- Run `git diff --check` and leave the worktree clean.

## Release preparation

The `Native release preparation` workflow is manual or tag-triggered. It builds
seven native targets, creates NAPI-RS platform packages, injects exact optional
platform dependencies into an ephemeral root package, and uploads all tarballs
with a SHA-256 manifest for inspection.

The workflow deliberately contains no `npm publish` command, GitHub release
creation, or npm credential handling. A maintainer must inspect the artifact and
deliberately add a separate trusted-publishing step in a future release. Follow
the current [NAPI-RS release guidance](https://napi.rs/docs/deep-dive/release)
when changing that process.
